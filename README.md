# upkg

Ever tried to document how to install your own program?

You end up writing 47 pages just to say "install the dev headers for libfoo", because on Debian it's `libfoo-dev`, on Fedora it's `libfoo-devel`, on Arch it's `libfoo`, on Alpine it's `libfoo-dev` (different one), on FreeBSD it's `foo`, and on macOS it's *"unidentified developer"*, because the dev didn't pay Apple's yearly tax to bless the binary.

**upkg lets you speak civilized. It speaks the dialect of 87 other package managers for you.**

```bash
upkg install git curl ripgrep
```

That's it. Same command on Debian, Fedora, Arch, openSUSE, OpenWrt, Termux, FreeBSD, DragonFly BSD, and macOS.

## What it actually does

- One command surface: `upkg install`, `upkg uninstall`, `upkg upgrade`.
- One file for the system packages a project needs: `upkg.toml`.
- Keeps a whole host current: `upkg refresh`, `upkg upgrade --full`, `upkg cleanup`, `upkg reboot-required`.
- Routes to the platform package manager where that is the right boundary, with a built-in Homebrew-compatible engine on macOS.
- Keeps the names people already know: no new catalog, no parallel universe.
- Stays out of your way for anything advanced. Use `apt`, `dnf`, `pacman`, `pkg` directly when you need to.

## What it is not

- Not a new global package ecosystem.
- Not a replacement for native tooling when you need flags, repos, or version pinning.
- Not a daemon, not a sync service, not a wrapper that "knows better."

## Backends

| Platform | Backend |
|---|---|
| Debian/Ubuntu | `apt` |
| Fedora/RHEL | `dnf` / `yum` |
| Arch | `pacman` |
| openSUSE | `zypper` |
| OpenWrt | `opkg` |
| Android (Termux) | `pkg` (fallback `apt`) |
| FreeBSD (+ GhostBSD, HardenedBSD) | `pkg` |
| DragonFly BSD | `pkg` (DPorts) |
| Any of the above with Ravenports | `rvn` (takes precedence when installed) |
| macOS | built-in engine (Homebrew-compatible names + prefixes) |

## Name aliasing

Most package names are identical everywhere, so upkg passes them straight
through to the native manager. The exceptions are packages that genuinely ship
under different names across managers, the classic case being development
headers: `libpq-dev` on Debian, `libpq-devel` on Fedora, `postgresql-libs` on
Arch.

For those, upkg keeps a small compiled-in alias catalog
(`src/catalog/aliases.toml`). It is **divergent names only** and is
deliberately not a registry: if a name is the same on every backend it is left
out. Resolution is exact-match with verbatim fallthrough, so an unknown name is
never rewritten or guessed at. The macOS engine resolves too, under the `brew`
key: `upkg install protobuf-compiler` installs the `protobuf` formula.

```toml
[libpq-dev]
upstream = "https://www.postgresql.org"
apt = "libpq-dev"
dnf = "libpq-devel"
pacman = "postgresql-libs"
```

Contributions are welcome. Every entry names one `upstream` so a reviewer can
confirm all the per-manager names are the same software, and entries must be
human-verified, not bulk-generated by an LLM. See the header of
`aliases.toml` for the full policy.

## macOS

No runtime switch, no shelling out to `brew`. The engine is built in and keeps the prefixes people expect:

- Apple Silicon: `/opt/homebrew`
- Intel: `/usr/local`

Same formula and cask names. Different engine.

Formula installs apply Homebrew's declarative `mkdir_p`, `link_dir`, and
`link_children` post-install metadata, including versioned runtime paths for
keg-only packages such as PostgreSQL. These links are retained across reinstalls
and removed on uninstall without deleting user data or third-party extensions.
Disabling ordinary global linking does not suppress these required runtime paths.
Ruby post-install scripts, database initialization, and service startup are not
executed; initialize PostgreSQL explicitly with `initdb` when needed.

When no compatible bottle exists, source installs support declarative file
installs and a guarded native recipe for Homebrew `coreutils` 9.12_1. The latter
requires Apple's Command Line Tools, installs build dependencies such as
`texinfo`, verifies the source and upstream patch, and builds without Ruby or
network access during compilation. GNU commands retain their `g` prefix;
unprefixed commands and manpages are also available under
`/opt/homebrew/opt/coreutils/libexec/gnubin` and `libexec/gnuman` (use
`/usr/local` on Intel). Changed formula logic is rejected until its native
recipe is reviewed; this is not a general Homebrew Ruby interpreter.

Apps are detected automatically when a name exists as a cask but not as a
formula. Use `--app` when you want to force cask resolution:

```bash
upkg install ghostty
upkg install --app ghostty
upkg install --app docker   # resolves the renamed docker-desktop cask
upkg uninstall --app ghostty
```

App installs are written in the Homebrew-compatible cask layout, so `brew
info --cask <name>` can detect them. Supported cask artifacts currently include
apps, binaries, manpages, bash/fish/zsh completions, and guarded postflight
symlinks. Renamed casks also resolve through Homebrew's `old_tokens` metadata.

## Install

```bash
curl -fsSL https://raw.githubusercontent.com/seuros/upkg/master/install.sh | sh
```

Or specify a custom install directory:

```bash
curl -fsSL https://raw.githubusercontent.com/seuros/upkg/master/install.sh | UPKG_INSTALL_DIR="$HOME/.local/bin" sh
```

If the install directory is not already in `PATH`, the installer adds it to
your shell profile (`.zshrc`, `.bashrc`, fish config, or `.profile`). Restart
your shell after install. Set `UPKG_NO_MODIFY_PATH=1` to skip this.

### CI (GitHub / Gitea / Forgejo Actions)

Use [`seuros/setup-upkg`](https://github.com/seuros/setup-upkg) to install upkg
in a workflow:

```yaml
steps:
  - uses: seuros/setup-upkg@master
  - run: upkg install imagemagick
  - run: upkg install   # whatever the repo's upkg.toml lists
```

`@master` tracks the latest action and installs the latest upkg release. Pin
both if you need reproducibility: `seuros/setup-upkg@v0.9.1` with
`with: { version: '0.10.0' }`. Works on GitHub Actions, Gitea Actions, and
Forgejo Actions.

## Usage

```bash
upkg install git curl
upkg install                      # what ./upkg.toml lists
upkg install --manifest ci/upkg.toml
upkg install ghostty
upkg install --app ghostty
upkg install --dry-run ripgrep
upkg uninstall htop
upkg uninstall --app ghostty
upkg upgrade
upkg refresh
upkg upgrade --full
upkg cleanup
upkg reboot-required --json
upkg list
upkg check git libpq-dev
upkg check                        # what ./upkg.toml lists
upkg search ripgrep
upkg search --app ghostty
upkg search --exact git
upkg --self-upgrade
upkg completion zsh
upkg help
```

Argument parsing and help are generated with `usage-rs`. Use `upkg --help`
for the command list and `upkg install --help` (or `upkg help install`)
for command-specific options. Existing command aliases, including
`upkg --self-upgrade`, remain supported.

Package commands and search retain flag-like positional values for compatibility.
Use `--` to treat all following tokens literally, including known options
(for example, `upkg search -- --exact`). Help flags now display help instead
of being treated as package names or search terms.
Running `upkg` without a command prints help to stderr and exits with status 2,
as does any other usage error.

### Shell completions

`upkg completion <shell>` prints a completion script for bash, zsh, fish,
powershell, elvish, or nu. The script asks the installed `upkg` binary for
candidates, so it stays current across upgrades.

```bash
upkg completion zsh > "${fpath[1]}/_upkg"
upkg completion fish > ~/.config/fish/completions/upkg.fish
upkg completion bash > ~/.local/share/bash-completion/completions/upkg
```

## upkg.toml

A project's system packages, the ones its build needs before `cargo build` or
`bundle install` can even start, go in `upkg.toml` at the repository root:

```toml
packages = ["protobuf-compiler", "pkg-config", "libssl-dev"]
```

Same names as on the command line, same alias catalog, same verbatim
fallthrough. Then, on a laptop, in CI, or in a fresh container:

```bash
upkg install            # installs what ./upkg.toml lists
upkg check              # says what's missing, needs no root
```

That's the whole format. Any other key is an error, not a shrug, so a typo
fails loudly instead of installing nothing. Names that start with `-` are
refused too: a package list is not a place to smuggle flags into a root
command.

upkg reads `./upkg.toml` only when you name no packages, and only from the
current directory: it never walks up the tree. `install` runs as root, and a
file three levels up (a monorepo root, someone's home directory) has no
business deciding what root installs. Run it where the file is, or say which
one with `--manifest PATH`.

## Check

`upkg check <package>...` answers whether packages are installed, for scripts
and deploy tools that verify a host before touching it. Names go through the
alias catalog first, so `upkg check libpq-dev` asks pacman about
`postgresql-libs`. It never needs root and never changes anything. With no
names, it checks what `./upkg.toml` (or `--manifest PATH`) lists.

```console
$ upkg check git llvm19
installed	git	git
missing	llvm19	llvm19
$ echo $?
1
```

Each line is tab-separated: `installed` or `missing`, the requested name, and
the native name it resolved to. The exit status is 0 when everything is
installed and 1 otherwise. The native tool's own explanation of a miss goes
to stderr.

| Platform | Asks |
|---|---|
| Debian/Ubuntu, Termux | `dpkg-query` (`ii`/`hi` count; `rc` leftovers do not) |
| Fedora/RHEL, openSUSE | `rpm -q` |
| Arch | `pacman -Q` |
| Alpine | `apk info -e` |
| OpenWrt | `opkg status` |
| FreeBSD, DragonFly BSD | `pkg info -e` |
| macOS | the built-in engine's installed kegs (formulae, or casks by token) |

Ravenports and Windows report that `check` is unsupported.

## Host maintenance

Four verbs keep a Linux or BSD machine current, for humans and for fleet
tools that patch bare-metal hosts on a schedule. They drive the OS's own
manager, even where Ravenports is installed (it manages `/raven`, not the
host), never stop to ask a question, and take `--dry-run` to print the plan
instead.

```bash
upkg refresh            # package metadata only
upkg upgrade --full     # everything: packages, new kernels, the base system
upkg cleanup            # orphaned packages and the package cache
upkg reboot-required    # one line; --json for one object
```

Plain `upkg upgrade` is unchanged. `upkg update` is an alias of `upgrade`,
not of `refresh`.

| Platform | `refresh` | `upgrade --full` | `cleanup` |
|---|---|---|---|
| Debian/Ubuntu | `apt-get update` | `apt-get full-upgrade -y` ¹ | `apt-get autoremove --purge -y`, `apt-get clean` |
| Fedora/RHEL | `dnf makecache` | `dnf upgrade -y` | `dnf autoremove -y`, `dnf clean all` |
| RHEL 7 / yum | `yum makecache` | `yum upgrade -y` | `yum autoremove -y`, `yum clean all` |
| Arch | nothing ² | `pacman -Syu --noconfirm` | `pacman -Rns --noconfirm` on `pacman -Qdtq`, then `pacman -Sc --noconfirm` |
| openSUSE Tumbleweed | `zypper --non-interactive refresh` | `zypper --non-interactive dist-upgrade` | `zypper --non-interactive clean` ³ |
| openSUSE Leap, SLES | `zypper --non-interactive refresh` | `zypper --non-interactive update` | `zypper --non-interactive clean` ³ |
| Alpine | `apk update` | `apk upgrade --update-cache` | `apk cache clean` |
| OpenWrt | `opkg update` | unsupported (that's `sysupgrade`) | nothing to clean |
| FreeBSD | `pkg update` | `pkg upgrade -y`, `freebsd-update fetch --not-running-from-cron`, `freebsd-update install` ⁴ | `pkg autoremove -y`, `pkg clean -ay` |
| DragonFly BSD | `pkg update` | `pkg upgrade -y` (base is `make world`) | `pkg autoremove -y`, `pkg clean -ay` |

1. With `DEBIAN_FRONTEND=noninteractive` and
   `-o Dpkg::Options::=--force-confdef -o Dpkg::Options::=--force-confold`:
   debconf never asks, and edited config files keep the local copy.
2. `pacman -Sy` without `-u` sets up a partial upgrade, which Arch does not
   support. `refresh` says so and exits 0; `upgrade --full` syncs.
3. zypper has no autoremove, so unneeded packages stay; `cleanup` says so.
4. With `PAGER=cat`. "No updates needed" and "No updates are available to
   install" (exit 2) count as success. On pkgbase systems, where
   freebsd-update refuses to run, `pkg upgrade` already covered the base and
   freebsd-update is skipped.

`cleanup` never removes the running kernel: apt protects the running, newest
and previous kernels from autoremove, dnf and yum protect the running one,
pacman's kernels are explicitly installed so `-Qdt` never lists them, and
FreeBSD's kernel lives in `/boot/kernel`, outside anything `pkg autoremove`
considers.

Commands that need root run as is for root, through `sudo` otherwise (or
`doas` where there is no sudo). Environment such as `DEBIAN_FRONTEND` goes on
sudo's command line (`sudo DEBIAN_FRONTEND=noninteractive apt-get ...`),
which sudoers allows for `ALL` or a rule tagged `SETENV`. A daemon that is
already root needs none of this.

### Reboot required

`upkg reboot-required` exits 0 whenever the check works, whatever the answer,
and non-zero only when the check itself failed.

```console
$ upkg reboot-required
reboot required: /var/run/reboot-required exists; packages: linux-image-6.1.0-26-amd64; since 2026-11-08T03:00:00Z
$ upkg reboot-required --json
{"required":true,"reason":"/var/run/reboot-required exists","packages":["linux-image-6.1.0-26-amd64"],"running_kernel":"6.1.0-25-amd64","installed_kernel":"6.1.0-26-amd64","since":"2026-11-08T03:00:00Z"}
```

`reason` explains a reboot, or why the check can't tell. `installed_kernel`
and `since` (RFC 3339, UTC) are `null` where they can't be determined.

| Platform | Asks |
|---|---|
| Debian/Ubuntu | `/var/run/reboot-required` and `.pkgs`; `since` is its mtime |
| Fedora/RHEL | `needs-restarting -r` (or `dnf needs-restarting -r`); exit 1 counts only with "Reboot is required" in its output, else kernels are compared |
| Arch | the running kernel's `/usr/lib/modules/$(uname -r)` is gone |
| Alpine, openSUSE, OpenWrt | the running kernel's modules are gone, or a newer kernel of the same flavor is installed |
| FreeBSD | `freebsd-version -k` differs from `uname -r`; fetched but uninstalled updates (`freebsd-update updatesready`) are mentioned in `reason` |
| DragonFly BSD | can't tell; says so |

With no kernels under `/usr/lib/modules` or `/lib/modules` (containers), the
answer is "not required", with a reason saying it can't tell.

### As a library

The same verbs are a Rust API, without the CLI's dependencies: the `host`
feature needs only std, serde and a TOML parser.

```toml
upkg = { version = "0.19", default-features = false, features = ["host"] }
```

```rust
use upkg::host::{Host, Options, Privilege};

let host = Host::detect()?;
let options = Options { dry_run: false, privilege: Privilege::AlreadyRoot };
host.refresh(&options)?;
let upgrade = host.full_upgrade(&options)?;
println!("changed: {:?}, packages: {:?}", upgrade.changed(), upgrade.changes());
host.cleanup(&options)?;
let status = host.reboot_required()?; // serde Serialize + Deserialize
```

Each task returns an `Outcome`: every command run, its exit code, the last
lines of its stdout and stderr, and what changed where the manager's summary
says so (`None` where it doesn't). A failed command returns
`Error::Failed`, which carries the outcome up to and including that step.
Commands and the reboot check's file reads go through the `Runner` trait;
`SystemRunner` runs real processes (captured, or echoed with
`SystemRunner::echoing()`), and a test can pass its own to `Host::new`.

`upkg.toml` is a library call away too, for tools that prepare machines from
a repository (a CI runner building a job's container or jail, say):

```rust
use upkg::host::{Host, Options, Privilege};
use upkg::manifest::Manifest;

let manifest = Manifest::load("upkg.toml")?;
let host = Host::detect()?;
let packages = manifest.resolve(host.platform().catalog_key());
let key = packages.key(); // "freebsd:pkgconf protobuf"
let options = Options { dry_run: false, privilege: Privilege::AlreadyRoot };
host.install(&packages, &options)?;
```

`resolve` takes any catalog key, so the set can be worked out before the
machine exists: `Platform::FreeBsd { pkgbase: false }.catalog_key()`, or
`Platform::from_os_release(..)` for a container image. A `PackageSet` holds
native names, sorted and deduplicated, and serializes as
`{"backend", "packages"}` to cross into a root helper. Its `key()` is the
backend, a colon, and those names joined by spaces: equal sets, equal keys,
whatever order the file used. The format is stable. It changes when the
catalog maps a name differently, which is a different set of packages and
should be a different cache entry; it does not identify the distribution
release, so fold the base image's identity in yourself.

`Host::install` is unattended: apt-get with debconf silenced (and
`apt-get update` first when apt never fetched an index, as in a fresh
container), `pkg` with `ASSUME_ALWAYS_YES` so a fresh jail bootstraps pkg
itself, pacman with `--needed`. It refuses a set resolved for another backend.

## Search

`upkg search <query>` routes to the platform's native search:

| Platform | Runs |
|---|---|
| Debian/Ubuntu | `apt search` |
| Fedora/RHEL | `dnf search` |
| Arch | `pacman -Ss` |
| openSUSE | `zypper search` |
| OpenWrt | `opkg find` |
| FreeBSD / DragonFly BSD | `pkg search` |
| Ravenports | `rvn search` |
| Android (Termux) | `pkg search` |
| Windows | `winget search` / `choco search` |
| macOS | built-in search against the Homebrew JSON index |

Output passes through verbatim on native backends so you get the
formatting you're used to. On macOS the engine prints a uniform
tab-separated line: `kind<TAB>name<TAB>version<TAB>description`.

Flags:

- `--app`: on macOS, restrict to casks. No-op (and rejected as
  `Unsupported`) on other platforms.
- `--exact`, `-e`: exact name match. Maps to `pkg/winget/choco/rvn -e`
  and to an anchored `^…$` regex for `pacman`/`opkg`. Returns an
  `Unsupported` error on managers without an exact mode
  (`apt`/`dnf`/`yum`/`zypper`).
- `--refresh`: macOS only. Forces revalidation of the cached Homebrew
  index instead of using the on-disk copy (default TTL 12 hours).

The macOS index lives at `<root>/cache/homebrew-search/` and is
revalidated with `If-None-Match` / `If-Modified-Since`. If the network
or server fails, a stale cached copy is used and a warning is printed
to stderr.
